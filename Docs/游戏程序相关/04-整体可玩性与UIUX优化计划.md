## 1. 结论与优化方向

当前项目的主要问题不是“功能不够”，而是已有功能缺少统一的玩家旅程、明确的前后因果和连续奖励反馈。

仓库已经具备建造、生存、采集、生产、探索、伙伴、编队、战斗、商人、目标、存档与离线结算等主体模块，也已经能通过正常 UI 进入。但这些模块目前仍以“功能面板”作为主要组织方式，玩家需要自己理解各系统的先后关系，操作结果也多以局部文字刷新结束，尚未充分形成：

```text
出现需求 → 明确下一步 → 执行动作 → 立即看到变化
→ 获得奖励/解决问题 → 解锁新选择 → 产生下一轮需求
```

本轮优化采用以下优先级：

1. **先串核心循环**：把现有系统编排成一段完整的 20–30 分钟新手旅程。
2. **再重做信息层级**：让界面告诉玩家“现在发生了什么、为什么、下一步做什么”。
3. **再补反馈与奖励**：每个关键操作都要有即时反馈、世界变化和下一步承接。
4. **最后扩充内容**：只有现有循环顺畅后，再增加事件、海域、设施和 Boss，避免继续堆叠孤立功能。

不建议本轮推翻现有 System / State / Command 架构，也不建议先做大规模美术替换。当前技术底座足以支撑优化，重点应放在玩法编排、表现协调和真实试玩验证。

## 2. 盘点基线

### 2.1 当前已有内容

截至 2026-08-06，仓库静态内容与可玩模块大致如下：

| 类别 | 当前数量/能力 | 说明 |
| --- | --- | --- |
| 物品 | 5 | 木材、生鱼、海水、淡水、烤鱼 |
| 设施 | 8 | 集雨器、篝火、维修站、储水罐、船舵、淡化器、渔网、储物架 |
| 配方 | 5 个定义，当前主链使用 4 条 | 淡水、烤鱼、维修、淡化、捕鱼相关流程 |
| 海域 | 5 | 起始海域、3 个方向海域及动态远洋入口 |
| 遭遇 | 7 | 资源、平静、风暴、4 名伙伴救援 |
| 伙伴 | 5 个定义 | 当前后续开发文档按 4 名可招募伙伴描述，应在内容核对时统一口径 |
| Boss | 2 | 教学 Boss、暗礁巨鳗 |
| 商人 | 1 | 3 个交易条目 |
| 新手目标 | 5 | 建造、探索、招募、扩建、Boss |
| 主体系统 | 已实现 | 建造、生存、生产、探索、伙伴、战斗、进度、商人、目标、保存/读取 |

### 2.2 当前界面结构

主游戏界面已经采用“中央世界画面 + 顶部信息 + 底部导航 + 侧边抽屉”的方向，基础框架合理：

- 中央区域负责海图或竹筏建造视图。
- 左上显示木材、食物等资源。
- 右上显示补给、耐久、体力。
- 底部提供航海图、设施、补给、伙伴、目标、商人六个入口。
- 详细功能在左侧抽屉中展示。

因此本轮应保留现有大框架，重点调整入口优先级、抽屉内容组织、关键反馈和小屏适配，不必重新搭建整套 UI 容器。

### 2.3 现状证据

本计划主要基于以下实际实现编制：

- `Scenes/Game/GameRoot.tscn` 与 `Src/UI/GameHudLayout.gd`：主界面层级、六入口导航、宽屏/紧凑布局。
- `Src/Core/Session/GameSession.gd`：现有系统已集中由会话持有，跨系统规则基础完整。
- `Src/Quest/QuestSystem.gd` 与 `Data/Quests/`：当前目标完成逻辑和五个目标定义。
- `Src/Exploration/`、`Src/Building/`、`Src/Production/`、`Src/Survivor/`、`Src/Battle/`：主要玩法入口与结果反馈。
- `Tools/playtest_balance.gd`：脚本化核心流程和平衡基线。
- 实际渲染检查：主菜单、主海图、目标、建造、补给面板（1280×720）。

## 3. 核心问题诊断

### 3.1 P0：玩家旅程没有真正形成顺序链

当前文档将五个新手目标描述为目标链，但 `QuestSystem.get_active_quests()` 会返回全部未完成目标，数据中也没有前置目标、章节、激活条件或顺序字段。因此新档会同时看到建造集雨器、前往西部浅滩、招募伙伴、扩建竹筏、击败 Boss 等多个目标。

实际首屏还存在提示竞争：

- 目标面板要求先建造集雨器。
- 航海标题区域提示先进入设施建造船舵。
- 中央引导文案又提示探索、打捞、升级设施。
- 底部六个入口全部以相近权重出现。

玩家能操作，但无法确定“游戏希望我先做什么”。

### 3.2 P0：系统间有数据连接，但缺少体验连接

已有系统在规则层已经相互影响，例如：

- 建船舵后解锁探索。
- 探索会消耗体力，并可能造成耐久损失或发现伙伴。
- 招募伙伴后可以编队并进入战斗。
- 建造生产设施后会自动产出物品。
- Boss 结算会发放物品、经验并影响耐久。

但玩家层面的承接仍较弱：

- 探索救援后，没有强提示直接承接到“查看并招募伙伴”。
- 风暴造成耐久损失后，没有直接承接到维修入口或缺少什么资源。
- 生产停摆只显示原因，没有把玩家引向对应解决动作。
- Boss 入口放在伙伴面板中，和“航行中发现威胁并准备挑战”的心智不一致。
- 商人作为常驻主导航入口存在，缺少“靠岸、停留、离开”的世界事件感。

### 3.3 P0：反馈链条主要停留在文字

当前大部分操作反馈集中在状态 Label：建造成功、航行结果、生产状态、交易结果、战斗结果。规则信息已经存在，但缺少分层表现：

1. 按钮/对象的即时响应。
2. 资源数字的增减动画。
3. 世界对象发生变化。
4. 目标完成与新目标激活。
5. 奖励、解锁或新的风险提示。

因此玩家容易产生“按钮点了，但不知道这件事对整个游戏有什么意义”的感受。

### 3.4 P1：信息架构按程序模块组织，不完全符合玩家心智

| 当前入口/内容 | 问题 | 建议心智 |
| --- | --- | --- |
| 补给面板同时放手动采集、食用、设施启停、库存 | 行为类型过多，按钮密集 | “生存补给”与“生产设施”分层，主界面只给当前最需要的行动 |
| 伙伴面板同时包含招募、升级、编队、Boss 挑战 | Boss 不属于伙伴管理 | Boss 入口由海图威胁、当前目标或战斗准备页承接 |
| 商人始终占一个主导航位 | 事件感与稀缺感弱 | 商人靠岸时出现情境入口，平时收纳到“更多/日志” |
| 目标占主导航位 | 玩家必须主动打开才能知道下一步 | 当前主目标固定展示，完整目标册作为二级页面 |
| 六个底部入口权重一致 | 新玩家选择负担高 | 4 个核心入口 + 1 个情境/更多入口，并突出推荐入口 |

### 3.5 P1：视觉完成度已有基础，但仍残留原型信息

- “竹筏建造（S1）”“生存状态（S2）”“采集与生产（S3）”等开发阶段标识仍出现在玩家界面。
- 顶部资源条只强调木材和食物，无法解释海水、生鱼、淡水等生产链资源，也没有容量和变化反馈。
- 1280×720 下底部导航高度较大，侧边抽屉、底部提示条和导航会同时侵占中央可玩区域。
- 建造列表主要是长按钮，设施差异、用途、运行状态和升级收益不够直观。
- 补给面板存在大量同级小按钮，缺少“当前推荐操作”。
- 颜色风格已经统一，但交互状态（选中、锁定、推荐、危险、完成）仍需形成稳定语义。

### 3.6 P1：脚本试玩验证了规则，却不能替代真实 UI 试玩

`Tools/playtest_balance.gd` 能证明指定 Seed 下的命令链和数值可以完成，但它会直接调用 Command，并知道正确路线、正确伙伴和正确 Boss。它无法覆盖：

- 玩家是否找得到入口。
- 玩家是否理解按钮含义。
- 玩家是否能从结果推断下一步。
- 面板切换、触摸热区和返回路径是否顺畅。
- 不同 Seed 下是否会因救援结果而卡住目标链。
- 等待生产期间玩家是否知道可以做什么。

后续验收必须同时包含脚本化测试和真人 UI 试玩。

## 4. 目标体验与量化标准

### 4.1 北极星体验

> 玩家在不断变化的海面上，为解决眼前生存问题建造设施；设施让玩家能够走得更远，远航带回资源与伙伴；伙伴和船筏成长又让玩家有能力应对更危险的海域和 Boss。

所有系统都应至少连接到这条链中的前一环和后一环，避免形成只消耗、不产出，或只产出、无用途的孤立模块。

### 4.2 首局体验目标

新玩家在不看外部攻略的情况下，应在 20–30 分钟内完成一次完整闭环：

```text
稳定补给
  → 建造船舵
  → 首次航行
  → 救援并招募伙伴
  → 扩建竹筏/改善生产
  → 进行战斗准备
  → 击败教学 Boss
  → 使用战利品交易或升级
  → 看见下一个海域目标
```

### 4.3 可量化验收指标

| 指标 | 目标 |
| --- | --- |
| 新档首次有效操作 | 30 秒内完成 |
| 首个目标完成 | 3 分钟内完成 |
| 玩家同时看到的“主目标” | 仅 1 个 |
| 从主目标到正确功能入口 | 最多 1 次明确点击 |
| 关键操作后的可见反馈 | 同帧或 0.2 秒内开始 |
| 首次完整闭环时长 | 20–30 分钟 |
| 新手流程阻断 | 0 个不可恢复死点 |
| 主流程中每 2–4 分钟 | 至少一次明确奖励、解锁或世界变化 |
| 1280×720 / 1920×1080 | 核心操作无重叠、无遮挡 |
| 触摸主操作热区 | 建议不小于 56×56 设计像素 |
| 键盘/手柄 | 主要页面焦点可预测、可返回 |

量化指标用于判断版本是否改善，不用于替代玩家访谈。真人试玩后还需记录“第一次迷路位置、第一次不知道为什么失败的位置、第一次感到重复的位置”。

## 5. 推荐的新手核心循环

### 5.1 20–30 分钟首局旅程

| 阶段 | 建议时长 | 玩家目标 | 串联系统 | 关键反馈/承接 |
| --- | ---: | --- | --- | --- |
| 1. 活下来 | 0–3 分钟 | 建造集雨器 | 目标、建造、生存 | 建成动画；首次产水倒计时；激活“获得并使用淡水” |
| 2. 学会维持 | 3–6 分钟 | 收集/使用第一份淡水 | 生产、库存、生存 | 补给条回升、资源飞入、解锁船舵目标 |
| 3. 获得移动能力 | 6–9 分钟 | 建造船舵 | 采集、建造、进度 | 海图从锁定变为可选；中央出现可航行路径 |
| 4. 第一次远航 | 9–13 分钟 | 前往西部浅滩 | 海图、体力、遭遇 | 体力预览；航行动画；遭遇结果卡 |
| 5. 获得伙伴 | 13–16 分钟 | 救援、招募并加入编队 | 遭遇、伙伴、编队 | 伙伴揭示卡；一键进入招募；编队战力变化 |
| 6. 扩张基地 | 16–20 分钟 | 扩建 Lv2，补一个生产/恢复设施 | 采集、建造、进度 | 甲板扩张动画；新设施/Boss 预告 |
| 7. 战斗准备 | 20–24 分钟 | 检查耐久、体力、编队与推荐战力 | 生存、伙伴、战斗 | 准备检查表；缺项可一键跳转修复 |
| 8. 教学 Boss | 24–28 分钟 | 完成首次战斗 | 战斗、奖励、经验、耐久 | 技能演出、Boss 意图、结算页、伙伴升级提示 |
| 9. 收束并抛钩 | 28–30 分钟 | 使用奖励交易/升级，看到新海域 | 商人、成长、海图 | 商人靠岸提示；下一海域风险与奖励预览 |

### 5.2 关键设计约束

- 首局目标必须按顺序激活，不能把后续 Boss 与扩建目标一次性全部展示。
- 不将教程做成长篇弹窗；教程应以当前目标、局部高亮和一次性提示完成。
- 每个阶段只介绍一个新概念，旧概念通过实际需求再次使用。
- 若随机遭遇会影响主线救援，应提供主线保底或将首次救援设为确定事件；不能让新手目标依赖指定 Seed。
- 生产等待应与其他短行为重叠，不能要求玩家停留在面板里看倒计时。
- 教学 Boss 入口应由海图威胁或主目标触发，不应长期固定在伙伴管理页。

## 6. UI/UX 总体方案

### 6.1 信息层级

推荐保留中央世界画面，将常驻 HUD 收敛为三类信息：

```text
┌ 资源与最近增减 ─── 当前主目标 / 区域 ─── 生存状态 / 菜单 ┐
│                                                          │
│                   海图 / 竹筏 / 战斗世界                  │
│                                                          │
│ [事件与奖励反馈]                      [情境行动/风险预览] │
│                                                          │
│        航海图       设施       生产       伙伴       更多 │
└──────────────────────────────────────────────────────────┘
```

原则如下：

- **顶部左侧：资源**。显示当前情境最相关的 3–5 项，支持 `+3`、`-2`、容量满等变化反馈。
- **顶部中间：主目标/区域**。只展示一个主目标、当前进度和推荐入口；航行时切换为区域和路径信息。
- **顶部右侧：生存**。补给、耐久、体力用紧凑图标与条形表达，正常时不占大面积，异常时展开原因和解决入口。
- **中央：世界变化**。海图、竹筏、航行、天气与事件必须成为主要视觉，不让面板长期盖住全部世界。
- **底部：核心导航**。建议保留航海图、设施、生产、伙伴四个固定入口，“目标”固定到顶部主目标，“商人”仅靠岸时出现，其他功能进入“更多”。

### 6.2 导航与抽屉

- 宽屏沿用左侧抽屉，但宽度建议保持在视口的 28%–34%，并为中央世界保留足够空间。
- 紧凑屏使用底部 Sheet，而不是让左侧抽屉覆盖中央全部内容。
- 同一时间只打开一个主抽屉；再次点击当前入口关闭并回到世界画面。
- 所有抽屉标题区统一包含：返回/关闭、标题、简短状态、帮助入口。
- 当前推荐入口增加轻微脉冲、高亮或目标标记；不能同时高亮多个入口。
- 锁定入口仍可查看，但必须显示“为什么锁定”和“一键前往解锁条件”，不能只是灰色不可点。

### 6.3 各页面优化

#### A. 主海图

- 海域节点显示距离/体力成本、风险等级、主要产出、是否含未知事件。
- 选中节点后再显示确认卡，避免“选择按钮列表 + 中央地图”重复表达。
- 航线用清晰路径和箭头表示；不可达原因显示在节点附近。
- 航行结果使用结果卡分层展示：到达、获得、损失、发现、下一步。
- 发现伙伴后提供“立即查看伙伴”主按钮和“稍后”次按钮。
- 遭遇风暴后提供“去维修”情境按钮。

#### B. 设施与建造

- 设施列表由长文本按钮改为分类卡：生存、生产、储存、航行。
- 卡片至少显示图标、用途、成本、占格、是否已建、解锁条件。
- 选中设施后进入放置模式，中央网格突出合法/非法格；确认区固定，不随列表滚动。
- 放置前显示收益预览，例如“每 45 秒产 1 淡水”“淡水容量 +30”。
- 升级显示前后对比，不只显示成本。
- 移除所有面向开发阶段的 `(S1)` 文案。

#### C. 生产与补给

- 将“手动采集”作为世界情境行动或单独的快速行动区，不与所有设施启停按钮混成一排。
- 每个设施采用状态卡：运行/停止/缺料/满仓、进度条、投入、产出、预计完成时间。
- 停摆原因必须带解决按钮：缺生鱼→去采集，产物满仓→查看库存/建储物架，补给耗尽→使用食物。
- 生存物品使用应在补给不足时自动提升优先级，并显示使用后的数值预览。
- 生产完成时资源从设施飞向资源栏，同时弹出简短 `+1`，不打断操作。
- 移除 `(S3)` 文案。

#### D. 伙伴与编队

- 分成“待救援/可招募”“已拥有”“出战编队”三个清晰区域。
- 顶部固定显示编队槽位和综合战力/生存能力，不把编队信息埋在文本中。
- 伙伴卡显示定位、等级、技能、升级收益；长描述放详情页。
- 招募后直接询问是否加入空编队位。
- Boss 挑战按钮移出伙伴面板，伙伴页只负责准备与成长。

#### E. 战斗

- 从居中通用面板升级为完整战斗画面：Boss 血条与意图、伙伴头像/生命、行动区、回合反馈。
- 普通攻击与技能按钮显示伤害/治疗预估、冷却和不可用原因。
- Boss 行动前给可理解的预告，使玩家有一次真实决策，而不是重复点击。
- 结算页分开显示战利品、经验、耐久变化、目标完成和新解锁。
- 返回主游戏后保留一条“刚才发生了什么”的摘要，避免场景切换后反馈消失。

#### F. 目标

- HUD 永久显示一个“当前主目标”，点击直接进入对应系统。
- 完整目标页按章节展示，未激活目标只显示模糊预告或隐藏。
- 目标完成时先显示完成反馈，再激活下一个目标。
- 初期不要求物品奖励；目标完成至少应带来新入口、新内容或明确世界变化。
- 后续若增加可领取物品奖励，必须设计幂等领取和库存满时的待领取状态。

#### G. 商人

- 商人从常驻功能改为靠岸事件：出现提示、停留状态、离开倒计时或本轮访问标记。
- 商品卡显示玩家持有数量、价格是否足够、购买后库存变化。
- 交易完成同时显示付出与获得，避免只显示“购买成功”。
- 商人首次出现应承接 Boss 奖励或过剩资源，形成资源回收用途。

### 6.4 反馈规范

每个关键动作至少覆盖下列五层中的三层：

| 层级 | 反馈 | 示例 |
| --- | --- | --- |
| 1. 输入反馈 | 按钮、格子、卡片立即响应 | 按下、选中、禁用原因 |
| 2. 数值反馈 | 资源/状态明确增减 | 木材 `-3`、淡水 `+1`、耐久 `-8` |
| 3. 世界反馈 | 场景对象发生变化 | 设施落位、甲板扩展、船只移动 |
| 4. 结果反馈 | 解释动作结果 | 获得物、损失、停摆、救援、胜负 |
| 5. 旅程反馈 | 承接下一步 | 目标完成、新目标、功能解锁、推荐入口 |

反馈应区分信息等级：

- 普通产出：轻量飘字，不打断。
- 目标完成/功能解锁：中等横幅或卡片，可自动消退。
- 新伙伴/Boss/关键剧情：可确认结果页。
- 行动失败：在操作附近解释原因，并提供可执行的解决方向。

### 6.5 视觉与可访问性

- 建立统一 Theme，不在各脚本中继续散落颜色、圆角和字号常量。
- 颜色语义固定：绿色=可执行/恢复，金色=推荐/目标，红色=危险/不足，灰色=锁定，蓝色=信息。
- 不仅依赖颜色，锁定、警告、完成还需图标和文字。
- 正文、按钮、资源数字建立统一字号层级；1280×720 下不得因字号过大压缩内容。
- 桌面 Hover、触摸 Press、键盘 Focus 都要有明确状态。
- 小屏安全区、超宽屏、触摸热区和文本换行统一进入场景验证清单。

## 7. 系统串联优化项

### 7.1 目标系统：从清单升级为旅程编排

**现状**：所有未完成目标同时活跃；读取完成状态时会派生并写入完成标记；缺少显式前置与激活反馈。

**优化**：

- 为 `QuestDefinition` 增加主线章节、排序、前置目标 ID 等数据；引用继续使用稳定 `StringName`。
- `QuestSystem` 提供“当前主目标”和“可见目标”查询，不再把所有未完成目标都视为活跃。
- 目标完成应通过明确的进度评估流程发生，并发出 `quest_completed`、`quest_activated` 等领域 Signal；纯读取接口不应产生隐藏状态修改。
- 完成标记保持可存档和幂等；旧档迁移要能推导当前目标。
- 首局补充“首次产水/使用补给”“设置编队”“战斗准备”等承接步骤。

### 7.2 探索结果：必须产生下一步行动

| 遭遇结果 | 现有影响 | 建议承接 |
| --- | --- | --- |
| 获得资源 | 入库 | 资源飞入、容量提示、可建造设施提示 |
| 平静海面 | 到达 | 显示海域发现度、下一个可探索方向 |
| 风暴 | 耐久损失 | 耐久条变化、维修入口、风险解释 |
| 伙伴救援 | 待招募 | 伙伴揭示卡、一键进入招募/编队 |
| Boss 威胁 | 进入战斗 | 准备检查表、推荐战力、稍后挑战标记 |

### 7.3 建造与生产：让设施解决具体问题

- 集雨器：解决补给，成为第一个设施教学。
- 船舵：解锁远航，承担主线门槛。
- 篝火/淡化器：把探索带回的原料转化为生存资源。
- 维修站：承接风暴和战斗的耐久损失。
- 储水罐/储物架：承接“产物满仓”，提供扩容目标。
- 渔网：提供离线/等待期产出，让玩家感到基地会运转。

设施卡必须明确显示它解决哪个问题；目标和停摆反馈应将玩家引向对应设施，而不是只给出系统名。

### 7.4 伙伴与战斗：形成“获得—培养—验证”闭环

```text
探索救援 → 伙伴揭示 → 招募 → 加入编队
→ 通过生产/探索获得升级资源 → 升级/调整编队
→ Boss 验证 → 经验与战利品 → 解锁更危险海域
```

教学 Boss 至少要验证一个玩家可理解的选择，例如治疗时机、技能冷却或 Boss 弱点。否则伙伴成长和战斗之间仍只会形成数值连接，无法形成策略体验。

### 7.5 商人与经济：承担资源转换角色

商人应优先解决两类问题：

1. 玩家某项关键资源短缺时，提供昂贵但可用的救急路径。
2. 玩家某项基础资源过剩时，提供转化为成长资源的出口。

首版无需复杂浮动价格，但商品组合必须与当前阶段需求相关，并由商人出现时机承接 Boss 战利品或探索过剩物。

## 8. 分阶段实施计划

工作量使用 S/M/L/XL 表示相对规模，不直接等同于日历工期。每个阶段完成后先试玩，再进入下一阶段。

### Phase A：核心旅程收口（P0，L）

**目标**：不用新增大量内容，先让现有系统真正构成一局完整游戏。

| ID | 优化项 | 工作量 | 依赖 | 验收 |
| --- | --- | ---: | --- | --- |
| PLAY-01 | 目标增加前置/排序/激活状态，只显示一个主目标 | M | Quest Definition/State/System | 新档不再同时展示五个目标 |
| PLAY-02 | 新增首次产水、使用补给、编队、战斗准备等承接目标 | M | PLAY-01 | 每个系统至少有前后承接 |
| PLAY-03 | 首次救援提供主线保底，不依赖指定 Seed | M | Exploration | 任意新档均可完成新手旅程 |
| PLAY-04 | Boss 入口从伙伴页迁到海图威胁/目标流程 | S | Scene flow/UI | 玩家从世界事件进入战斗 |
| PLAY-05 | 目标完成、下一目标激活、功能解锁统一反馈 | M | PLAY-01/UIRoot | 完成后无需自行寻找下一步 |
| PLAY-06 | 风暴、停产、库存满等失败状态增加解决入口 | M | 各 View | 错误反馈能直接导向修复动作 |

**阶段出口**：5 名不熟悉项目的试玩者中，至少 4 名能在无口头提示的情况下完成首个“建造→生产→航行→招募→战斗”闭环。

### Phase B：HUD 与导航重构（P0，L）

**目标**：建立清晰主次，不让六个系统入口同时争夺注意力。

| ID | 优化项 | 工作量 | 验收 |
| --- | --- | ---: | --- |
| UX-01 | 顶部主目标卡，取代目标常驻底部入口 | M | 当前目标、进度、推荐操作始终可见 |
| UX-02 | 生存 HUD 紧凑化，异常时展开 | M | 正常状态减少占屏，警告仍清晰 |
| UX-03 | 资源栏支持情境资源、容量和增减反馈 | M | 所有库存变化可被感知 |
| UX-04 | 底部导航收敛为 4 个核心入口 + 更多/情境入口 | M | 1280×720 中央可玩区域明显增大 |
| UX-05 | 宽屏侧抽屉、紧凑屏底部 Sheet 统一规则 | M | 目标分辨率无遮挡、可返回 |
| UX-06 | 移除 S1/S2/S3 等原型标识并统一玩家文案 | S | 游戏界面无开发阶段术语 |
| UX-07 | 抽取统一 Theme 和交互状态样式 | M | 不再由多个脚本各自定义主样式 |

### Phase C：关键页面与反馈升级（P0/P1，XL）

**目标**：让每个关键动作具有即时、结果和旅程三层反馈。

| ID | 优化项 | 优先级 | 工作量 | 验收 |
| --- | --- | ---: | ---: | --- |
| FEED-01 | 通用 Toast/奖励飘字/目标完成横幅 | P0 | M | 资源、完成、错误反馈分层展示 |
| FEED-02 | 探索结果卡与一键承接 | P0 | M | 救援/风暴/资源均有明确下一步 |
| FEED-03 | 建造卡片、收益预览和固定确认区 | P0 | L | 放置前能理解成本和收益 |
| FEED-04 | 生产设施卡、进度、停摆原因与解决按钮 | P0 | L | 不再依赖密集启停按钮和长文本 |
| FEED-05 | 伙伴卡与编队槽位重构 | P1 | L | 招募、编队、升级关系一眼可见 |
| FEED-06 | 战斗场景信息层级与结算页 | P0 | XL | Boss 意图、技能、结算和返回承接完整 |
| FEED-07 | 商人靠岸事件与双向交易反馈 | P1 | M | 商人不再像永久设置页 |

### Phase D：内容密度与中期钩子（P1，L）

**前置条件**：Phase A–C 的真人试玩已证明入口和反馈顺畅。

- 为每个核心海域补 2–3 个具有选择的事件，不只重复资源/平静/风暴。
- 给海域增加清晰主题、风险标签和主要产出差异。
- 让至少 3 个设施在主流程中产生明确用途，不只作为可选按钮存在。
- 教学 Boss 加入一个可预告、可应对的机制；区域 Boss 加入不同机制。
- 为首个 Boss 后增加一个短期目标和一个中期目标，避免结算后失去方向。
- 商人货物根据阶段或本轮事件变化，先做小规模数据驱动，不做复杂经济模拟。

内容数量建议以试玩密度为准，不以“把数据表填满”为目标。第一轮可先补 6–8 个事件、3–5 个目标和 1 套 Boss 机制。

### Phase E：发布前体验质量（P0，L）

- 横屏安全区、1280×720、1920×1080、超宽屏与紧凑屏验证。
- 鼠标、键盘、手柄、触摸的焦点、返回和热区验证。
- 离线结算、存档损坏恢复、战斗中断、窗口失焦、长时间生产验证。
- UI 文本、本地化、截断、数值极值和库存满场景验证。
- 音效、动效、震动等反馈可按平台逐步接入，但不阻塞规则验证。
- 进行至少两轮新玩家试玩：首轮找阻断，次轮验证修改是否有效。

## 9. 技术落地建议

### 9.1 保持现有架构边界

- `GameSession` 继续持有玩法 System；不新增 Autoload。
- `GameState` 只保存状态，不放目标编排、奖励发放或导航规则。
- UI 只创建 Command、调用公开查询和监听 Signal，不直接修改状态。
- 旅程进度归 `QuestState/QuestSystem`；商人出现节奏归 `MerchantState/MerchantSystem`；纯表现反馈归 UI 节点。
- 不创建万能 `UIManager` 或 `GameManager`。

### 9.2 建议的数据与接口调整

| 范围 | 建议 |
| --- | --- |
| QuestDefinition | 增加 `chapter_id`、`sort_order`、`prerequisite_quest_ids` 等稳定 ID/字段；是否增加奖励引用应在奖励领取方案确认后再做 |
| QuestState | 保留完成 ID；若有待领取奖励，再增加明确的待领取/已领取状态并做存档迁移 |
| QuestSystem | 增加当前主目标、可见目标、显式评估流程；读接口不产生隐藏写入 |
| SessionEvents/领域 Signal | 增加目标激活/进度/完成等必要 Signal；优先使用现有各 System 的领域 Signal，不扩成万能事件总线 |
| GameRoot/UIRoot | 增加只负责表现的反馈协调节点，监听结果并显示 Toast、目标横幅、结果卡；不得修改 State |
| GameHudLayout | 继续负责 UI 模式切换，增加统一导航状态和宽屏/紧凑屏布局规则 |
| MerchantState | 若引入访问时机，保存当前是否靠岸、库存及必要时间/次数；规则由 MerchantSystem 校验 |

### 9.3 首批可能涉及的文件

- 目标链：`Src/Data/Definitions/QuestDefinition.gd`、`Src/Quest/QuestSystem.gd`、`Src/Core/State/QuestState.gd`、`Data/Quests/`。
- 会话编排：`Src/Core/Session/GameSession.gd`、`Src/Core/Events/SessionEvents.gd`。
- 主界面：`Scenes/Game/GameRoot.tscn`、`Src/UI/GameHudLayout.gd`、`Src/SceneFlow/GameRoot.gd`。
- 目标与反馈：`Src/Quest/View/GoalPanel.gd`、`Src/UI/UIRoot.gd`，以及新增的单一职责表现组件。
- 玩法页面：各 Feature 的 `View/` 目录，不将规则下沉到 View。
- 本地化：`Translations/game_text.csv`，移除开发阶段用语并补齐新反馈。
- 测试：`Tests/Unit/test_quest_system.gd`、相关 Feature 单元测试、`Tests/Integration/` 新增首局闭环测试。

## 10. 测试与试玩方案

### 10.1 自动化测试

#### 单元测试

- 目标前置、排序、激活、完成与旧档迁移。
- 同一完成事件重复处理不重复奖励或解锁。
- 不同 Seed 下的新手主线救援保底。
- 风暴/生产停摆/库存满后的公开查询能返回解决所需信息。
- 商人出现状态和交易保持原子性。

#### 集成测试

增加一条不直接访问内部 State 的首局流程测试：

```text
新建游戏 → 建集雨器 → 获得/使用淡水 → 建船舵
→ 首航 → 救援 → 招募/编队 → 扩建 → 教学 Boss
→ 结算 → 保存 → 读取 → 当前主目标一致
```

同时保留 `Tools/playtest_balance.gd` 作为数值回归，但新增多 Seed 检查，不能只验证参考 Seed 6。

#### 场景/UI 流程验证

- 主目标跳转到正确面板。
- 打开/关闭/返回路径一致。
- 宽屏侧抽屉和紧凑屏底部 Sheet 不重叠导航与确认按钮。
- 键盘/手柄焦点不会落到隐藏面板。
- 所有锁定按钮有可读原因。

涉及 Gameplay/Core/Data/Save 的改动，必须运行：

```powershell
.\Tools\verify_project.ps1 -GodotPath <Godot可执行文件> -Full
git diff --check
```

### 10.2 真人试玩记录

每轮至少记录：

- 首次有效操作和首个目标完成时间。
- 每次主动打开错误面板的位置。
- 每次停留超过 20 秒仍不知道做什么的位置。
- 每次操作后询问“发生了什么/为什么/接下来做什么”的回答。

建议录像或逐步记时，但不引入联网分析或账号系统。开发期可使用本地分类日志和人工观察。

## 11. 优先级总表

### 必须先做（P0）

1. 单一主目标、顺序激活和保底新手路径。
2. 首局 20–30 分钟核心旅程串联。
3. 目标完成/新目标/功能解锁反馈。
4. 探索、风暴、救援、停产结果的一键承接。
5. HUD 主次、导航收敛与原型文案清理。
6. 建造、生产、战斗三个核心页面的可理解反馈。
7. 多分辨率、触摸和焦点验证。

### 完成 P0 后做（P1）

1. 商人靠岸节奏和经济用途。
2. 伙伴卡、编队和成长表现升级。
3. 海域差异、选择事件和 Boss 机制。
4. 更完整的目标章节、奖励和中期钩子。
5. 音效、动效和氛围表现。

### 暂缓（P2）

- 大规模新增资源种类、十级船型、复杂研究树。
- 多舰队、完整天气/昼夜、复杂浮动经济。
- 社交、联网、账号、云同步或玩家市场。
- 在核心循环未验证前制作大量正式美术资源。

## 12. 推荐的第一批开发任务

第一批建议只取一个可独立验收的纵切，不同时铺开所有页面：

1. 把五个目标改为真正顺序激活，并增加“首次产水/使用淡水”目标。
2. 主界面顶部增加当前主目标和“去完成”，底部暂时保留原导航，先验证引导效果。
3. 目标完成时显示完成横幅并自动切换到下一目标。
4. 首次救援改为主线保底，并在结果卡中提供“查看伙伴”。
5. 将教学 Boss 入口从伙伴面板移到主目标/海图威胁流程。
6. 用 3–5 名新玩家进行一次 20–30 分钟试玩，再决定导航和页面重构细节。

这批任务完成后，项目应从“多个能用的功能面板”变成“有明确开始、推进、高潮和下一步的完整试玩”。随后再进入 Phase B/C 的全面 UI/UX 提升，返工风险最低。

---

## 13. 整体完成定义

满足以下条件后，可认为本轮整体优化完成：

- 任意正常新档都能通过 UI 完成首局完整闭环，不依赖开发者知识或指定 Seed。
- 玩家任何时刻都能从 HUD 看出当前主目标，并在一次明确操作内前往正确入口。
- 建造、生产、探索、救援、战斗和交易完成后，均能看见数值/世界结果及下一步承接。
- 目标、解锁、奖励和存档状态一致，重复加载或重复事件不产生二次结算。
- UI 不再出现开发阶段标识，主要页面在目标分辨率和输入方式下可正常使用。
- 自动化完整验证通过，并完成至少两轮真人试玩闭环。
- 真人试玩中不再出现共性的“我不知道现在要做什么”阻断；剩余问题进入明确的 P1/P2 backlog。
