## 1. 计划目标与实施原则

本计划将项目推进至可验证的单机 2D 核心玩法 MVP。MVP 的玩家循环保持为：

```text
探索航行 → 遭遇 / 资源 / 伙伴 → 收集与加工 → 建造与扩建
    → 生存维持 → 编队与战斗 → 奖励和成长 → 下一次探索
```

当前实现遵循以下优先级：

1. 同一系统发生冲突时，以最新、最细的策划案为玩法口径；
2. 所有程序实现必须遵守 `Architecture.md`、`DataDesign.md` 与 `CommandAndEvents.md`；
3. `系统关系架构文档.md` 中的高层系统图用于说明玩法依赖，不能覆盖当前工程的 `GameSession → System → State` 边界；
4. 先完成一条可保存、可测试、可从正常 UI 推进的链路，再扩充内容数量；
5. 不新增玩法 Autoload、万能 Manager、联网、账号、云存档或第三方玩法框架。

每项功能的完成条件不只是“存在脚本或场景”，而是同时具备：真实玩家入口、明确的 State 修改权、Definition 配置、存档策略、自动测试及桌面/触摸主流程验证。

## 5. 当前优先事项：R0 生存与指令收口（P0，工作量 M）

**目标**：让 S4 能以稳定的公开接口消耗体力、造成耐久影响、在读档时完成幂等的离线生存结算；同时保持 UI 不直接修改 State。

### R0-01：补齐 SurvivalSystem 的行动规则接口

- 增加面向调用方的“可否行动 / 原子消耗体力 / 应用耐久损耗”公开接口；接口返回明确成功或失败结果，不让 Exploration/Battle 直接写 `SurvivalState`。
- 行动类型、消耗量和失败码使用 `StringName` 或数据配置；探索与战斗都复用同一套预检规则。
- 补齐补给归零、耐久归零和体力不足时的允许/禁止行为，并通过 Signal 为 UI 提供反馈。
- 为不足体力、边界值、一次性扣除、耐久归零、补给归零后的规则新增纯逻辑单元测试。

### R0-02：实现离线生存结算与存档幂等性

- 在明确的读档激活入口计算 `max(now - last_online, 0)`，调用 `SurvivalCalculator.calculate_offline()`，更新状态、时间戳与已结算标记。
- 离线补给遵守最低保留 1、耐久不离线损耗、体力按配置恢复；重复载入同一存档不得重复结算。
- 定义轻量 `OfflineSettlementReport` 或等价只读结果供 UI 展示；报告不是权威 State，也不保存 Node。
- 补齐 0、1、4、8 小时、超长离线、时钟倒退、重复结算、旧存档迁移的测试；将离线面板接入 GameRoot 的正常读档流程。

### R0-03：统一 Command 的进入路径

- 为 Gather、UseFood、SetProductionEnabled 注册 SessionCommandSystem 处理分支，保持成功/失败结果和 `command_rejected` 事件一致。
- View 仍只创建 Command；GameSession 继续是 State/System 的拥有者。不得为此新增全局 Command Manager。
- 用现有建造、采集、食用、设施启停分别覆盖成功、失败和拒绝事件测试。

**R0 验收**：探索系统无需访问 `SurvivalState` 内部容器即可完成行动预检与扣除；离线结算可重入且可保存；完整测试和 `git diff --check` 通过；桌面和触摸下的现有生存/生产操作未回归。

## 6. MVP 分阶段开发计划

### S4：大地图与确定性探索闭环（P0，工作量 XL）

**玩家可感知结果**：建造并解锁船舵后，玩家可在起始海域与 2–3 个相邻六边形海域间航行；预览成本并确认行动；获得确定性资源、空事件或风暴结果，再回到竹筏循环。

**实施顺序**：

1. `RegionDefinition`、`EncounterDefinition`、最小 `WorldState`：当前位置、已发现区域、已消费一次性事件与世界随机状态；所有引用使用 `StringName`。
2. 纯规则 `ExplorationSystem`：相邻性、发现、解锁条件、行动成本、原子扣除和结果对象；先接入 R0 的体力/耐久接口。
3. `RandomService` 独立 exploration 流：相同 world seed 与相同状态必得相同遭遇，不污染未来 battle 流。
4. 三种最小遭遇：资源发现、空事件、风暴；奖励经 InventorySystem 发放，风暴经 SurvivalSystem 处理耐久影响。
5. 地图 View：可达性、成本预览、确认/取消、遭遇结果及返回竹筏。View 只读状态和结果。
6. 存档：当前位置、已发现状态、一次性事件和必要随机状态完整往返。

**暂不包含**：完整天气系统、昼夜、真实海域温度、幸存者救援、交易和 Boss。天气作为后续独立模块，S4 仅预留环境修正输入接口，不用临时硬编码天气规则。

**测试重点**：不可跨格、资源不足不出发、失败无部分扣费、同 Seed 同遭遇、一次性事件不重复、风暴耐久损耗、读档后世界状态一致。

### S5：伙伴卡牌与编队（P1，工作量 L）

**目标**：由探索救援获得 3–4 名伙伴，支持详情、Lv1–Lv10 升级和 2–3 个出战位。

- 定义 Survivor/Skill Definition、SurvivorInstance、SurvivorState 和稳定 ID；同一唯一伙伴不得重复招募。
- 实现 Recruit、Upgrade、SetLineup Commands 及 SurvivorSystem，所有消耗经 InventorySystem 原子处理。
- 先提供最小被动效果查询接口；组合加成、品质突破和完整故事不进入 MVP。
- 接入救援遭遇、卡牌/编队 UI、存档往返及触摸友好替换操作。

### S6：教学 Boss 战（P0，工作量 XL）

**目标**：当前编队可挑战一个教学 Boss，使用普通攻击和至少一个技能，获得胜负、掉落和返回主游戏的完整结果。

- 定义 Boss/Skill/Reward Definition 与 BattleState；BattleSystem 为纯规则，不依赖动画帧或具体场景节点。
- 进场通过 R0 的接口预扣一次体力并校验耐久；战斗回合内不再扣体力。
- 使用独立 battle 随机流；结果通过明确接口结算掉落、伙伴经验和耐久影响，避免直接操作其他模块内部容器。
- 先实现教学 Boss；区域 Boss 作为 S7 内容补齐。BattleRoot 只表现状态变化与行动意图。

### S7：MVP 整合、引导与平衡（P0，工作量 XL）

**目标**：新玩家能在约 20 分钟内自然完成一次“探索→收集→扩建→招募→战斗→成长”。

- 实现竹筏 Lv1→Lv3、3×3→5×6 扩建、船舵解锁及 ProgressionSystem；UI 不自行判断解锁条件。
- 将设施扩充至 7–10 个、海域至 3–4 个、伙伴至 3–4 名，并补齐教学 Boss + 区域 Boss。
- 增加一个数据驱动的流浪商人模板，交易经 InventorySystem 原子交换。
- 建立数据驱动的新手目标与导航；完成建造、背包、地图、伙伴、战斗、离线面板之间的返回路径。
- 完成 20–30 分钟试玩，平衡补给消耗、恢复、产能、航行、奖励与战斗；记录调参依据。

### S8：发布质量与 MVP 后内容（P1/P2，持续）

先做真机性能、横屏/安全区、触摸热区、键盘/手柄焦点、设置、音效、基础可访问性、存档损坏/备份恢复和长时间运行验证。之后再按试玩结果扩展天气、更多海域/遭遇/设施/伙伴/Boss、任务、据点与叙事。

不进入当前 MVP：完整 10+ 海域地图、复杂程序化世界、卡牌组合加成、品质突破、完整剧情/据点、抽卡、广告/付费、社交/排行榜、账号/云同步/联机、ECS、C#、SQLite 和大型第三方框架。

## 8. 每阶段通用完成定义

一个阶段只有同时满足以下条件才可标记完成：

1. 数据归属、System 修改权、Command/Signal 流向清楚，UI 不直接写 State；
2. 可调数值进入 Definition/配置文件，稳定引用使用 `StringName`；
3. 新增 State/Instance 已序列化，旧档有迁移测试或明确拒绝策略；
4. 规则有单元测试，跨模块链路有集成验证，随机逻辑使用固定 Seed；
5. `git diff --check` 与 `Tools/verify_project.ps1 -GodotPath <Godot可执行文件> -Full` 通过；
6. 正常、失败、返回流程可操作，错误反馈可理解；
7. 桌面与触摸至少各验证一次关键流程，并检查横屏安全区；
8. 逻辑不绑定渲染帧，离线与长时间结算用公式或批量周期计算；
9. 不混入未授权 Autoload、第三方框架、联网、账号、云同步或无关重构。
