## 1. 计划目标

本计划用于把当前的“框架与空场景工程”推进到可验证的核心玩法 MVP。目标不是一次性实现完整游戏，而是按依赖顺序逐步建立以下闭环：

```text
收集资源 → 扩建竹筏 → 维持生存 → 航行探索
    ↑                              ↓
生产与恢复 ← 伙伴成长 ← 战斗与奖励 ← 遭遇事件
```

每个阶段必须同时交付：

1. 玩家可感知的可玩结果；
2. Definition / State / System / Command / Signal 的清晰边界；
3. 存档兼容方案；
4. 自动测试或可重复的集成验证；
5. 对桌面与移动端输入、UI 和性能影响的检查。

本计划不以“类、目录或占位场景已经存在”作为功能完成标准。

## 2. 当前项目基线

### 2.1 已具备的基础

| 领域 | 当前状态 | 可复用内容 |
| --- | --- | --- |
| 工程与规范 | 已建立 | Godot 工程、Typed GDScript、目录规范、ID/数据/Command/Signal/存档等架构文档 |
| 启动与场景流 | 基础可用 | Bootstrap、SceneRouter、主菜单、空 GameRoot、空 BattleRoot、UIRoot |
| 会话与状态 | 骨架可用 | GameSession、GameState，以及 Raft/Inventory/Survivor/World/Battle/Progression 状态入口 |
| 数据加载 | 最小闭环可用 | ItemDefinition、BuildingDefinition、JSON Loader、DataRegistry、ID 校验 |
| 通用运行时 | 基础可用 | SimulationClock、RandomService、SaveService、CommandResult、基础日志与调试入口 |
| 空间规则 | 纯逻辑基础可用 | 等距 GridMath、RaftGrid、六边形 HexGrid |
| 平台基础 | 骨架可用 | 语义化 InputService、响应式 UI、安全区、画质档位与性能指标 |
| 当前内容 | 极少 | `item_wood`、`building_rain_collector`、主菜单背景及少量占位场景 |

### 2.2 尚未形成的玩法

- `InventoryState`、`SurvivorState`、`WorldState`、`BattleState`、`ProgressionState` 仍是占位状态。
- `PlaceBuildingCommand` 已定义，但尚无正式 `BuildingSystem` 处理建造、扣费和实例 ID。
- 没有采集、配方、生产、设施运转、储存上限与资源溢出规则。
- 没有 SurvivalState / SurvivalSystem，补给、耐久、体力、警告和离线结算均未实现。
- 没有可操作的竹筏主视图、建造预览、HUD、背包、地图、伙伴编队或战斗界面。
- 没有区域 Definition、探索事件、天气、伙伴卡牌、技能、Boss、交易和教程流程。
- SaveService 当前主要保存木筏状态，其他玩法状态尚未序列化；迁移链也需随首个玩法状态一起校正。
- 原有 GUT gitlink 缺少可解析的子模块元数据；S0 将以仓库内置的零依赖测试运行器恢复可复现的完整测试基线。

### 2.3 当前结论

框架阶段已经提供了正确的扩展方向，但项目尚未完成第一个 Gameplay 垂直切片。后续不应继续横向增加通用框架，而应沿“建造 → 生存 → 生产 → 探索 → 伙伴 → 战斗”的关键路径持续产出可玩闭环。

## 3. 策划口径与实现前决策门

### 3.1 文档优先级

出现冲突时按以下顺序处理：

1. 同一系统的最新详细策划案；
2. 核心玩法原型方案；
3. 游戏立项方案；
4. 旧技术方案中的示例设计。

因此，生存系统以 `03-生存系统策划案.md` 为当前实现依据：玩家管理“补给、耐久”两项生存指标，以及独立的行动资源“体力”；旧原型中的“士气”不进入当前 MVP，除非后续策划重新确认。

### 3.2 必须先锁定的规则

| 决策编号 | 问题 | 建议默认口径 | 最晚确认阶段 |
| --- | --- | --- | --- |
| D00 | 生存策划版本与关联文档口径 | 已在生存策划案 v0.6 中统一为“最新确认版本” | 已确认 |
| D01 | 体力上限、探索/战斗消耗、离线恢复、行动补给消耗 | 已确认全部由 `stamina_config` 读取；S2 不在代码中硬编码，测试 fixture 可使用独立样例值 | 已确认 |
| D02 | 厨房既“产出烤鱼”又“持续恢复补给”，存在重复收益歧义 | 厨房和蒸馏器仅生产食物；补给由手动进食、被动休整和伙伴技能恢复 | 已确认 |
| D03 | 补给生产数据存在数量级过高风险 | 保留公式与配置能力，S7 通过 20–30 分钟试玩重新定值 | S3 / S7 |
| D04 | 耐久环境叠加与事件公式 | 统一使用 `基础损耗 × (1 + 耐久修正系数之和)`；天气影响暂不启用，仅保留接口 | 已确认 |
| D05 | 战斗体力扣除时机 | 进入一场战斗前预扣一次；战斗回合、攻击和技能不再扣除 | 已确认 |
| D06 | 归零恢复状态的 UI 映射 | `> 0` 解除惩罚与引导；超过警告线立即恢复正常视觉；安全线仅结束内部恢复状态与加速 | 已确认 |
| D07 | 离线补给与收益 | 补给结算最低保留 1，不设时长上限；离线收益前 4 小时 100%，第 5 小时起每小时 ×0.9 | 已确认 |

未确认时可采用表中的建议默认值推进原型，但必须保留配置项，并在对应阶段记录实际采用值，不把临时值写死在 System 或 UI 中。

### 3.3 数据结构规范化

策划案中的“数据表”应解释为可版本控制的 Definition 与运行时 State，而不是数据库表：

- 不引入 `player_id`、数据库时间戳、JSON 嵌套库存字段或 SQLite。
- 所有 Definition、跨模块引用和事件引用使用 `StringName` 稳定 ID，不使用策划表中的整数 ID。
- 食物继续属于 ItemDefinition；厨房、维修站、储水罐等属于 BuildingDefinition；生产关系属于 RecipeDefinition。
- SurvivalState 只保存本局数值、状态和结算时间；规则、阈值和速率属于 SurvivalConfigDefinition。
- 新增 `survival`、`weather` 等 ID 前缀前，必须同步更新 `DataDesign.md` 与 `IdValidator.ALLOWED_PREFIXES`。

### 3.4 Tick 与真实时间

现有 `SimulationClock` 是每秒 5 个模拟 Tick；策划中的 `SurvivalTick` 是每 5 秒结算一次。实现时不修改全局时钟频率，而是在 SurvivalSystem 内累计模拟时间，每满 5 秒结算一次。这样生产、动画表现和未来系统仍可使用各自频率。

离线结算不得依赖场景树或循环模拟。纯规则函数接收“上次离线时间、当前时间、配置与状态”，一次性计算结果；测试传入固定时间，正式流程才读取系统时间。

## 4. 目标模块边界

| 模块 | Definition | State / Instance | System 规则 | View 更新方式 |
| --- | --- | --- | --- | --- |
| Inventory | ItemDefinition | InventoryState | InventorySystem 负责增减、容量、原子校验 | 监听 `inventory_changed` 后查询 |
| Building | BuildingDefinition | RaftState / BuildingInstance | BuildingSystem 负责放置、拆除、成本和实例 ID | 监听 `building_placed/removed` 后按 ID 重建 |
| Production | RecipeDefinition | ProductionInstance 或建筑运行状态 | ProductionSystem 负责周期、原料、产出和停摆原因 | 监听生产状态与库存事件 |
| Survival | SurvivalConfigDefinition | SurvivalState | SurvivalSystem 负责消耗、恢复、警告、惩罚和离线结算 | HUD 监听数值/状态变化后查询 |
| WorldMap | RegionDefinition / EncounterDefinition | WorldState | ExplorationSystem 负责相邻移动、航行成本和遭遇 | 地图 View 只显示可达性与结果 |
| Survivor | SurvivorDefinition / SkillDefinition | SurvivorInstance / SurvivorState | SurvivorSystem 负责招募、升级、编队 | 卡牌 UI 通过 Command 调整编队 |
| Battle | BossDefinition / SkillDefinition | BattleState | BattleSystem 负责回合、伤害、胜负和奖励 | BattleRoot 只播放状态变化 |
| Progression | ProgressionDefinition | ProgressionState | ProgressionSystem 负责解锁条件和一次性奖励 | UI 监听 `progression_unlocked` |

GameSession 持有各 Gameplay System 及其事件对象；GameState 只聚合可存档状态。不得新增玩法 Autoload，也不得创建万能 Manager 或全局事件总线。

## 5. 实施路线总览

```text
S0 验证基线收口
  ↓
S1 竹筏建造垂直切片
  ↓
S2 生存核心（补给/耐久/体力）
  ↓
S3 采集、生产与恢复闭环
  ↓
S4 大地图与探索闭环
  ↓
S5 伙伴卡牌与编队
  ↓
S6 回合制战斗与 Boss
  ↓
S7 MVP 整合、引导与平衡
  ↓
S8 发布质量与内容扩展
```

工作量使用相对等级表示：S 为小、M 为中、L 为大、XL 为跨模块大型任务。它用于控制任务粒度，不代表日历工期。

## 6. 分阶段开发计划

### S0：验证基线收口（优先级 P0，工作量 M）

**玩家可感知结果**：主菜单能稳定进入空游戏，开发者可用一条命令判断当前提交是否可运行。

**任务**：

- S0-01：提供仓库内置的零依赖测试运行器，使全新检出仓库可执行 `Tools/verify_project.ps1 -Full`，不依赖失效的 GUT gitlink 或本机缓存。
- S0-02：把现有验证脚本、内置测试用例与 README / AGENTS.md 的命令统一，确保错误返回非零退出码。
- S0-03：校正 SaveService 的版本号与迁移入口，为后续新增状态建立 v1 → v2 的真实测试。
- S0-04：为 DataRegistry 补齐非法 JSON、重复 ID、未知 ID 与跨 Definition 类型重复 ID 测试；首个 Definition 引用字段落地时再补充引用完整性测试。
- S0-05：给现有 Sandbox 标记“可运行示例”或“占位场景”，避免把空场景误判为模块完成。

**验收**：

- 干净检出后无需个人缓存即可完成快速验证和完整测试。
- Godot 编辑器加载、项目 headless 启动、现有验证脚本及单元测试全部通过。
- 失败测试、资源解析错误和脚本错误均使统一命令失败。

### S1：竹筏建造垂直切片（P0，工作量 L）

**实施状态（2026-08-02）：已完成首个可玩闭环。** 初始新游戏会发放 10 木材；雨水收集器消耗 3 木材，可在 3×3 竹筏上通过选择、预览、确认或取消完成放置。库存、建筑实例和占用格会一并存档；命令失败不会扣除材料。临时水面背景为可替换的 AI 生成资源。

**玩家可感知结果**：开始新游戏后，玩家拥有木材，可在初始 3×3 竹筏上放置一个合法的 1×1 建筑；非法位置会给出原因，读档后建筑仍存在。

**任务**：

- S1-01：实现 InventoryState / InventorySystem，支持查询、原子增减与非负约束。
- S1-02：扩展 ItemDefinition 和 BuildingDefinition，增加建造成本、分类、占地与最小显示字段。
- S1-03：实现 BuildingSystem，正式处理 PlaceBuildingCommand；先校验 Definition、库存、占格与旋转，再一次性扣费并创建实例。
- S1-04：定义稳定且可存档的 BuildingInstance ID 生成策略，禁止使用显示名或 Node 路径。
- S1-05：制作 BuildingSandbox 与 GameRoot 的最小等距网格、建筑选择、放置预览、确认/取消和错误提示。
- S1-06：把 InventoryState、RaftState 和 BuildingInstance 纳入 SaveService，并添加往返与迁移测试。

**测试重点**：余额不足、无效 ID、越界、重叠、旋转 footprint、失败不扣费、重复命令、保存/读取一致性。

**阶段出口**：完成框架文档中定义的“竹筏建造基础垂直切片”，并在桌面鼠标与触摸模拟输入下完成同一放置流程。

### S2：生存核心垂直切片（P0，工作量 L）

**玩家可感知结果**：HUD 显示补给、耐久和体力；时间推进会改变指标；玩家可用物品恢复补给、消耗材料修船；低值与归零状态有明确反馈；重启后状态正确恢复。

**任务**：

- S2-01：按已确认的 D01、D04、D06、D07 创建 SurvivalConfigDefinition 与最小配置数据。
- S2-02：实现 SurvivalState，保存当前值、阈值状态、体力恢复余量、上次在线时间和必要的幂等结算标记。
- S2-03：实现纯逻辑 SurvivalCalculator，覆盖截断、持续消耗、加法修正上限、状态转换与离线公式。
- S2-04：实现 SurvivalSystem，由 GameSession 持有并订阅 SimulationClock；内部累计到 5 秒后结算。
- S2-05：实现 UseFoodCommand、RepairRaftCommand，以及探索/战斗可调用的体力预检与消耗接口。
- S2-06：制作最小 SurvivalHUD、低阈值警告、归零提示、恢复倒计时和离线结算面板。
- S2-07：升级存档版本并添加旧档默认值、离线 0/1/8/超过 8 小时、重复结算测试。

**暂不包含**：天气随机切换、真实海域温度、厨房/维修站自动恢复、伙伴技能恢复。这些依赖后续系统，只使用固定修正 fixture 验证接口。

**测试重点**：大步长与小步长结果一致、暂停不消耗、倍速正确、数值上下限、跨阈值事件只发一次、体力恢复余量不丢失、设备时间倒退时不产生收益。

### S3：采集、生产与恢复闭环（P0，工作量 XL）

**实施记录（2026-08-04）**：D02 采用“设施只生产物品、补给仅由手动使用食物恢复”的口径；首条可玩链为木材/生鱼采集 → 篝火生产烤鱼 → 手动恢复补给，以及集雨器生产淡水 → 手动恢复补给。D03 的首批容量使用数据 Definition 配置：烤鱼 10、淡水 20，储水罐将淡水容量提高至 50；数值平衡仍留待 S7 的试玩调整。

**玩家可感知结果**：玩家可以获得原料，建造并运行集雨器/篝火或厨房等设施，生产食物与淡水，再用于维持补给；维修设施可以恢复耐久。

**任务**：

- S3-01：锁定 D02、D03，定义 RecipeDefinition、生产周期、输入输出与设施能力标签。
- S3-02：实现最小采集入口，为木材、生鱼、海水等原料提供可测试来源。
- S3-03：实现 ProductionSystem，按累计时间批量计算完成周期，不按帧修改库存。
- S3-04：实现设施启停、原料不足、产物满仓、恢复加速与停摆原因查询。
- S3-05：实现物品容量与储存设施加成；容量溢出行为必须有明确反馈和测试。
- S3-06：加入 MVP 所需的第一组 Item / Building / Recipe 数据，先控制在 3–5 个设施和一条完整生产链。
- S3-07：制作设施状态面板、生产进度、缺料提示和补给使用入口。

**建议首条闭环**：

```text
拾取木材/生鱼/海水
  → 建造集雨器与烹饪设施
  → 生产淡水/烤鱼
  → 手动恢复补给
  → 继续采集与扩建
```

**阶段出口**：连续运行 30 分钟不会出现负库存、重复产出、读档后进度回退或 UI 与 State 不一致。

### S4：大地图与探索闭环（P0，工作量 XL）

**玩家可感知结果**：玩家建造船舵后打开六边形地图，在 3–4 个海域之间航行，消耗体力与补给，并通过确定性遭遇获得资源。

**任务**：

- S4-01：定义 RegionDefinition、EncounterDefinition 和 WorldState 的已发现、当前位置、清理状态。
- S4-02：实现 ExplorationSystem，校验相邻格、解锁条件、体力、耐久禁战状态与航行成本。
- S4-03：接入 RandomService 独立流，固定 Seed 可重现遭遇但不污染战斗随机序列。
- S4-04：实现资源发现、空事件和风暴三种最小遭遇；事件奖励经 InventorySystem 发放。
- S4-05：接入昼夜与海域温度修正；天气先实现晴天/暴雨两种最小状态，不扩展完整天气内容。
- S4-06：制作地图 View、目标预览、可达性、航行确认和遭遇结果界面。
- S4-07：保存当前位置、已发现区域、已消费的一次性事件和随机流所需状态。

**测试重点**：不可跨格、资源不足不出发、命令失败无部分扣费、同 Seed 同遭遇、一次性事件不重复、环境修正进入/离开时正确更新。

### S5：伙伴卡牌与编队（P1，工作量 L）

**玩家可感知结果**：玩家可通过探索救援获得 3–4 名伙伴，查看卡牌、升级并调整 2–3 个出战位。

**任务**：

- S5-01：扩展 SurvivorDefinition，加入定位、品质、基础属性、成长曲线、技能 ID 与展示引用。
- S5-02：实现 SurvivorState / SurvivorInstance 的招募、经验/等级和队伍槽位数据。
- S5-03：实现 SurvivorSystem 与 Recruit/Upgrade/SetLineup Commands，完整校验消耗和解锁条件。
- S5-04：实现最小 SkillDefinition 与被动效果查询接口；暂不制作组合加成和品质突破。
- S5-05：将探索救援接入招募，并保证同一唯一伙伴不会被重复招募。
- S5-06：制作卡牌列表、详情、升级和编队 UI；拖拽之外必须提供触屏友好的点击替换方式。

**测试重点**：重复招募、等级上限、升级成本、槽位锁定、同一伙伴重复上阵、存档往返、被动加成来源可追踪。

### S6：回合制战斗与 Boss（P0，工作量 XL）

**玩家可感知结果**：玩家可用当前编队挑战教学 Boss，进行普通攻击和至少一个技能，获得胜负结果、掉落和耐久影响，并返回主游戏。

**任务**：

- S6-01：按已确认的 D05 定义 BattleDefinition / BossDefinition、技能效果和奖励表。
- S6-02：实现 BattleState 与纯逻辑 BattleSystem；回合顺序、伤害、冷却、倒下、胜负均不依赖动画帧。
- S6-03：所有随机判定使用独立 battle 随机流；测试可注入固定 Seed。
- S6-04：实现 StartBattleCommand 与 BattleActionCommand；进入战斗前原子校验体力和耐久。
- S6-05：战斗结束通过明确结果接口结算掉落、伙伴成长与竹筏耐久，避免 BattleSystem 直接改其他模块内部容器。
- S6-06：制作 BattleRoot 的教学 Boss 表现、行动按钮、下一回合预告、胜利/失败和返回流程。
- S6-07：加入 1 个教学 Boss 与 1 个区域 Boss；每个只实现足以验证策略差异的 1–3 个技能。

**测试重点**：伤害下限、克制关系、冷却、目标倒下、全员倒下、奖励只发一次、失败扣耐久、耐久为零禁止开战、切换场景不丢 Session。

### S7：MVP 整合、引导与平衡（P0，工作量 XL）

**玩家可感知结果**：新玩家能在 20–30 分钟内完成至少一轮“探索 → 收集 → 扩建 → 招募 → 战斗 → 成长”，并理解补给、耐久和体力的作用。

**任务**：

- S7-01：实现 Raft Lv1 → Lv3 的 ProgressionSystem 与功能解锁，避免 UI 自行判断阶段。
- S7-02：补足 MVP 的 7–10 个设施、3–4 个海域、3–4 名伙伴、2 个 Boss 和基础资源/配方数据。
- S7-03：实现一个流浪商人模板；交易通过 InventorySystem 原子交换，不引入经济 Manager。
- S7-04：实现数据驱动的新手引导与推荐目标，UI 只提交正常 Command，不走旁路修改状态。
- S7-05：完成主 HUD、建造、背包、地图、伙伴、战斗和离线面板之间的导航与返回栈。
- S7-06：按策划成功标准进行 20–30 分钟试玩，调整消耗、恢复、产能、航行和战斗数据。
- S7-07：完成新游戏、存档、读档、离线回来、战斗返回和异常退出后的端到端测试。

**MVP 出口标准**：

- 测试者可在 20 分钟左右自然完成一轮完整核心循环。
- 建造、生产、生存、探索、伙伴、战斗、成长均有真实数据流，不依赖 DebugPanel 才能推进。
- 关键失败都有明确原因，且不会留下半扣资源、重复奖励或不可恢复的状态。
- 存档覆盖全部权威 State / Instance，不保存 Node；旧档有迁移或明确拒绝策略。
- 桌面与手机横屏的关键操作均可完成，关键 UI 不被安全区域遮挡。

## 8. 每阶段通用完成定义

一个阶段只有同时满足以下条件才可标记完成：

1. **架构**：数据归属、System 修改权、Command/Signal 流向清晰，UI 不直接写 State。
2. **配置**：可调数值进入 Definition/配置文件，稳定引用使用 StringName ID。
3. **存档**：新增 State 已序列化；旧版本加载行为有迁移测试或明确拒绝策略。
4. **测试**：新增规则有单元测试；跨模块闭环有集成测试；随机使用固定 Seed。
5. **验证**：`git diff --check` 与适用的 `Tools/verify_project.ps1 -Full` 通过。
6. **体验**：正常流程、失败流程、返回流程均可操作；错误反馈可理解。
7. **平台**：桌面与触摸至少各验证一次主要操作；UI 检查安全区和横屏窄宽度。
8. **性能**：不把逻辑绑定渲染帧；离线与长时间结算使用公式或批量周期数，不逐 Tick 追赶。
9. **范围**：没有混入未授权 Autoload、第三方框架、联网、账号、云同步或无关重构。

## 9. 推荐任务拆分规则

后续单个 Codex 开发任务建议控制在一个可独立验收的行为内，例如：

- “实现 InventorySystem 的原子增减和测试”，而不是“完成全部资源系统”。
- “实现 PlaceBuildingCommand 的校验与扣费”，而不是“完成竹筏建造”。
- “实现 SurvivalCalculator 的补给消耗与阈值状态机”，而不是“完成生存系统”。
- “实现固定 Seed 的资源遭遇”，而不是“完成探索系统”。

每个任务说明必须包含：允许修改目录、输入 Definition/State、公开接口、失败与边界行为、存档影响、测试命令和明确不包含项。跨模块任务应先定义接口，再分别实现提供方与消费方。
