# 《沧海余生》开发前框架准备方案

> 项目代号：X001 / OceanHome  
> 文档版本：v0.1  
> 文档性质：开发前框架准备与验收方案  
> 适用范围：Godot 4.x、纯单机、2D 等距竹筏建造、六边形海域探索、伙伴与回合制 Boss 战斗

---

## 1. 文档目标

本方案用于在正式实现玩法前，建立可长期维护、可测试、可由 Codex 分模块持续开发的工程基础。

框架阶段的目标不是做出大量可玩的内容，而是先确定：游戏数据放在哪里、规则由谁执行、画面如何同步、系统如何通信、如何保存、如何测试，以及新模块以什么方式接入工程。

完成本阶段后，项目应能够安全进入第一个 Gameplay 垂直切片：**等距竹筏网格 → 建造放置 → 背包 → 建筑实例**。

---

## 2. 框架阶段核心原则

1. **Typed GDScript only**：变量、参数、返回值及容器尽可能显式标注类型。
2. **Data / System / View 分离**：Data 保存状态，System 执行规则，View 只负责输入与表现。
3. **Definition / Instance / View 分离**：静态定义、存档中的运行时实例、场景中的显示节点不可混为一谈。
4. **UI 不直接修改状态**：UI 发出 Command；System 校验并修改 State；状态变化通过 Signal 通知表现层。
5. **少量 Autoload**：仅保留真正跨存档、全生命周期的服务；玩法系统由 `GameSession` 持有。
6. **数据驱动优先**：物品、建筑、配方、伙伴、技能、Boss、事件、区域和任务使用稳定 ID 与 Definition 数据。
7. **确定性优先**：随机数必须可注入 Seed，逻辑 Tick 必须可控，便于重现 Bug 和编写测试。
8. **先可测试，再扩展**：纯规则尽量以 `RefCounted` 编写，不依赖渲染或场景树。
9. **单机优先**：不为联机、服务器、账号、社交或云端同步预建复杂抽象。
10. **模块边界优先**：禁止“万能 Manager”；跨模块沟通优先使用明确接口、命令或信号。

## 4. 框架模块清单（F01–F27）

### F01：Godot 工程基础设置

- **职责**：创建可启动的 Godot 工程；统一渲染器、显示、拉伸、输入和调试设置。
- **核心接口**：`Bootstrap` 场景；`ProjectSettings` 中的显示与输入配置。
- **目录位置**：`project.godot`、`Scenes/Bootstrap/Bootstrap.tscn`、`Src/Core/Bootstrap.gd`。
- **Codex任务**：配置 2D Compatibility Renderer、1920×1080 设计分辨率与拉伸策略；创建最小启动场景；建立必要输入动作。
- **验收标准**：工程可在编辑器和 headless 模式启动；启动场景无脚本错误；窗口在常见比例下不出现关键 UI 被裁切的基础问题。

### F02：Git 与工程卫生

- **职责**：建立可追踪、可还原且不提交 Godot 缓存的版本管理基础。
- **核心接口**：`.gitignore`、提交规范、分支与验证约定。
- **目录位置**：仓库根目录。
- **Codex任务**：创建适用于 Godot 的 `.gitignore`；写明不提交 `.godot/`、导出产物、用户存档与本机 IDE 文件的规则；补充 README 中的启动与验证说明。
- **验收标准**：`git status` 不显示 Godot 缓存；可完成一次干净的初始提交；克隆后能重新导入并启动项目。

### F03：架构与编码规范

- **职责**：将 Data / System / View、依赖方向、命名、类型、错误处理与测试要求固化为团队规则。
- **核心接口**：`AGENTS.md`、`Docs/游戏程序相关/架构/Architecture.md`、`Docs/游戏程序相关/架构/CodingStandard.md`。
- **目录位置**：仓库根目录与 `Docs/游戏程序相关/架构/`。
- **Codex任务**：编写面向 Codex 的项目规则：Typed GDScript、禁止 UI 直改状态、禁止新增 Autoload 未经批准、禁止巨型 Manager、每个玩法系统的测试要求和验证命令。
- **验收标准**：新开发者只阅读上述文档即可知道新文件应放的位置、依赖限制及最低验证步骤。

### F04：稳定 ID 与命名体系

- **职责**：让存档、配置、事件、任务和运行时引用使用不随显示文本变化的稳定主键。
- **核心接口**：`StringName` ID；`IdValidator.is_valid_id(id: StringName) -> bool`；ID 命名规则。
- **目录位置**：`Src/Data/`、`Docs/游戏程序相关/架构/DataDesign.md`。
- **Codex任务**：定义 ID 格式与前缀规则，例如 `item_wood`、`building_rain_collector`、`survivor_lao_chen`、`boss_giant_squid`；建立重复 ID 检查工具。
- **验收标准**：显示名称可修改而存档引用不受影响；加载数据时重复或非法 ID 会给出明确错误。

### F05：GameSession 与 GameState

- **职责**：表示一次新游戏或读档后的完整运行生命周期；集中保存状态但不承载业务规则。
- **核心接口**：`GameSession.create_new_game(seed: int) -> void`、`GameSession.load_state(state: GameState) -> void`、`GameSession.dispose() -> void`；`GameState`。
- **目录位置**：`Src/Core/Session/`、`Src/Core/State/`。
- **Codex任务**：实现可创建、加载、销毁的 `GameSession`；定义空的 `GameState` 及 `raft_state`、`inventory_state`、`survivor_state`、`world_state`、`battle_state`、`progression_state` 的占位数据对象。
- **验收标准**：连续新建与销毁 Session 不残留旧状态；加载指定 GameState 后各子状态可被准确读取；GameState 不直接执行建造、生产等玩法逻辑。

### F06：Definition / Instance 数据模型

- **职责**：明确静态内容定义、玩家拥有实例、场景显示对象三者的边界。
- **核心接口**：`ItemDefinition`、`BuildingDefinition`、`SurvivorDefinition`；`BuildingInstance`、`SurvivorInstance`；对应 View 合约。
- **目录位置**：`Src/Data/Definitions/`、`Src/*/`、`Data/`。
- **Codex任务**：提供最小示例 Definition 和 Instance；定义可序列化字段、运行时字段与显示字段分别允许出现在哪里。
- **验收标准**：一份 BuildingDefinition 可以派生多个 BuildingInstance；存档不保存 Node；View 被销毁或重建不会丢失实例状态。

### F07：DataRegistry 与数据加载

- **职责**：统一加载并查询静态配置，避免模块各自扫描目录或硬编码资源路径。
- **核心接口**：`DataRegistry.load_all() -> bool`、`get_item(id: StringName)`、`get_building(id: StringName)`、`has_definition(id: StringName) -> bool`。
- **目录位置**：`Src/Data/Registry/`、`Src/Data/Loading/`、`Data/`。
- **Codex任务**：选择 JSON 或 Godot Resource 作为第一批 Definition 格式并保持一致；实现注册、校验、查询、重复 ID 报错；提供少量 fixture 数据。
- **验收标准**：可加载示例物品与建筑；未知 ID 和重复 ID 都会明确失败；Gameplay System 不需要了解文件路径。

### F08：Command 与 Signal 通信规范

- **职责**：建立玩家输入、教程、测试与系统执行规则之间的统一入口；防止循环调用。
- **核心接口**：`PlaceBuildingCommand` 等参数对象；领域信号如 `inventory_changed`、`building_placed`、`battle_started`。
- **目录位置**：`Src/Core/Commands/`、`Src/Core/Events/`。
- **Codex任务**：写明 Command 由谁创建、由谁处理、如何报告成功或失败；定义信号命名和 payload 规则；提供一个演示命令闭环。
- **验收标准**：UI 可以只创建 Command 而不知道 State 内部结构；系统校验失败不会部分修改状态；信号含义和携带数据在文档中可查。

### F09：SimulationClock

- **职责**：将渲染帧率和经营逻辑时间分离，为暂停、倍速、离线结算和确定性测试提供基础。
- **核心接口**：`start()`、`pause()`、`set_speed(multiplier: float)`、`advance(delta: float)`、`simulation_tick(delta_seconds: float)`。
- **目录位置**：`Src/Core/Simulation/`。
- **Codex任务**：实现默认 5 Tick/s 的逻辑时钟，支持 0、1、2、4 倍速；明确累积时间和单帧最大补偿 Tick 的策略。
- **验收标准**：同样的输入时间得到相同 Tick 数；暂停时不触发模拟；2 倍速在相同真实时间内产生约两倍逻辑时间；无无限补帧风险。

### F10：RandomService 与 Seed 策略

- **职责**：集中管理随机性，允许复现世界生成、战斗、事件和掉落结果。
- **核心接口**：`set_world_seed(seed: int)`、`get_stream(stream_id: StringName)`、`roll_chance(chance: float) -> bool`、`range_i(minimum: int, maximum: int) -> int`。
- **目录位置**：`Src/Core/Random/`。
- **Codex任务**：基于 `RandomNumberGenerator` 建立按用途分流的随机流，如 `world`、`event`、`loot`、`battle`；禁止 Gameplay 中直接调用全局随机 API。
- **验收标准**：相同种子和相同调用顺序得到相同结果；不同随机流的调用不会意外改变另一个流的结果；测试能注入固定种子。

### F11：SaveService 与 SaveMigrator

- **职责**：实现新建、保存、读取、备份及版本迁移的最小闭环。
- **核心接口**：`new_game()`、`save_game(slot_id: StringName) -> bool`、`load_game(slot_id: StringName) -> GameState`、`migrate(data: Dictionary) -> Dictionary`。
- **目录位置**：`Src/Save/`。
- **Codex任务**：定义 JSON 顶层结构，包括 `save_version`、`game_state`、`world_seed`；实现原子写入或备份策略；预留 `v1_to_v2` 迁移入口。
- **验收标准**：保存后重启项目可加载等价 GameState；损坏文件不会覆盖有效备份；未知未来版本被安全拒绝；缺省字段可经过迁移或默认值处理。

### F12：SceneRouter 与游戏流程

- **职责**：管理启动、主菜单、游戏主场景、战斗场景和返回流程，避免任意节点自行切场景。
- **核心接口**：`go_to_main_menu()`、`enter_game(session: GameSession)`、`enter_battle(context)`、`return_to_game()`。
- **目录位置**：`Src/SceneFlow/`、`Scenes/Bootstrap/`、`Scenes/Game/`、`Scenes/Battle/`。
- **Codex任务**：建立最小转场状态机；明确 Session 在场景切换时保留还是销毁；添加错误回退到主菜单的处理。
- **验收标准**：可从启动进入空 Game Scene 并返回主菜单；进入和退出 Battle Scene 后 Session 状态仍然正确；不会产生重复 UI Root 或重复 Session。

### F13：UIRoot 与窗口层级

- **职责**：统一 HUD、普通窗口、模态弹窗、Tooltip、教程、过场与 Esc 返回规则。
- **核心接口**：`open_window(window_id: StringName, context: Variant)`、`close_topmost()`、`show_popup(...)`、`show_tooltip(...)`。
- **目录位置**：`Src/UI/`、`Scenes/UI/`。
- **Codex任务**：建立 `UIRoot`、`HUDLayer`、`WindowLayer`、`PopupLayer`、`TooltipLayer`、`TutorialLayer`、`TransitionLayer`；定义窗口栈和遮罩策略。
- **验收标准**：同一窗口不会重复打开；Esc 先关闭最上层可关闭界面；模态窗口能阻止底层点击；UI 不直接写 GameState。

### F14：等距 GridMath

- **职责**：提供竹筏等距网格的纯数学坐标转换和鼠标选格基础。
- **核心接口**：`grid_to_world(cell: Vector2i) -> Vector2`、`world_to_grid(position: Vector2) -> Vector2i`、`get_cell_polygon(cell: Vector2i) -> PackedVector2Array`。
- **目录位置**：`Src/Raft/GridMath.gd`、`Tests/Unit/Raft/`。
- **Codex任务**：根据确定的格子宽高实现双向转换；处理负坐标、边界和浮点误差；不要依赖 Camera 或 Node。
- **验收标准**：任意测试格子经 `grid_to_world` 再 `world_to_grid` 可回到原格；典型边界点选择结果符合约定；纯单元测试可运行。

### F15：RaftGrid 状态与占格规则

- **职责**：管理木筏甲板、建筑占格、有效边界、邻接关系及未来寻路所需的可通行信息。
- **核心接口**：`can_place(footprint, origin, rotation) -> bool`、`place(instance) -> bool`、`remove(instance_id: StringName) -> bool`、`is_walkable(cell: Vector2i) -> bool`。
- **目录位置**：`Src/Raft/`。
- **Codex任务**：实现与 View 无关的 RaftState/RaftGrid；支持最小 3×3 初始木筏和示例 1×1、2×2 建筑 footprint；发出网格变化事件。
- **验收标准**：不能在不存在的甲板或已占用格放置；放置与拆除后占格信息一致；相邻/连通规则有测试；存档恢复后网格一致。

### F16：HexGrid 世界地图坐标

- **职责**：提供与竹筏 Grid 完全独立的六边形海域坐标、邻居、距离、方向及显示转换。
- **核心接口**：`HexCoord`、`get_neighbors(coord)`、`distance_to(a, b) -> int`、`hex_to_world(coord) -> Vector2`、`world_to_hex(position) -> HexCoord`。
- **目录位置**：`Src/WorldMap/`、`Tests/Unit/WorldMap/`。
- **Codex任务**：选定 axial 或 cube 坐标并记录选择原因；定义六方向枚举；实现无 UI 依赖的数学与测试。
- **验收标准**：相邻格距离为 1；距离满足对称性；坐标与世界位置可稳定往返；不与 RaftGrid 共用坐标规则或类名。

### F17：对象创建与生命周期约定

- **职责**：规定 Definition、Instance、View 的创建、绑定、重建与销毁方式，避免 View 成为真实数据源。
- **核心接口**：`BuildingView.bind_instance(instance_id: StringName)`、`ViewFactory.create_*()`；`unbind()`、`dispose()` 约定。
- **目录位置**：`Src/Shared/`、各玩法模块的 `View/` 子目录。
- **Codex任务**：定义 View 绑定 ID、从 Session 查询实例、监听状态更新、释放信号连接的通用模式；提供一个最小 BuildingView 示例。
- **验收标准**：重载场景后可按实例 ID 重建相同表现；删除实例后 View 不再持有无效引用；逻辑测试无需实例化 View。

### F18：日志与错误处理

- **职责**：让开发期问题可检索、可分类、不会被零散 `print()` 淹没。
- **核心接口**：`GameLogger.info(category, message)`、`warning(...)`、`error(...)`、`assert_or_log(condition, ...)`。
- **目录位置**：`Src/Core/Debug/`。
- **Codex任务**：定义 `SAVE`、`DATA`、`RAFT`、`WORLD`、`BATTLE`、`UI` 等分类；规定开发环境断言和发行版本 fallback 原则。
- **验收标准**：数据缺失、读档失败和非法建造均可从日志定位原因；不在核心系统中散落无分类 `print()`；不会静默吞掉关键错误。

### F19：自动测试框架（GUT）

- **职责**：为纯逻辑系统提供可重复运行的单元与集成测试能力。
- **核心接口**：GUT 测试目录、test doubles、fixture 数据和测试运行配置。
- **目录位置**：`Tests/Unit/`、`Tests/Integration/`、`Tests/Fixtures/`。
- **Codex任务**：安装或接入适配当前 Godot 版本的 GUT；创建示例测试；为 GridMath、RandomService、SaveService 至少各增加一条测试。
- **验收标准**：可从命令行运行测试并返回正确退出码；失败测试会显示文件、用例和断言；测试无需人工打开游戏画面。

### F20：Headless 验证入口

- **职责**：将脚本加载、项目启动与自动测试整合为每次玩法改动后的最低验证流程。
- **核心接口**：`Tools/verify_project.*` 或等价统一命令；CI 可调用的退出码。
- **目录位置**：`Tools/`、`AGENTS.md`。
- **Codex任务**：提供 Godot headless 检查与 GUT 运行命令；把命令写入 AGENTS.md；区分“快速语法/加载检查”和“完整测试”。
- **验收标准**：开发者可用一条命令获取成功或失败；脚本语法错误、资源加载错误、测试失败都会令验证失败；命令不依赖个人路径。

### F21：DebugPanel 与开发命令

- **职责**：缩短验证玩法的路径，避免每次都通过正常游戏进度制造测试条件。
- **核心接口**：`DebugCommand`；`add_item()`、`set_game_time()`、`spawn_survivor()`、`teleport_hex()`、`start_battle()`。
- **目录位置**：`Src/Core/Debug/`、`Scenes/Dev/`。
- **Codex任务**：实现仅开发环境可用的 DebugPanel 或快捷命令入口；命令仍通过系统接口，不直接篡改 View。
- **验收标准**：可在开发构建中快速修改资源、时间、位置和战斗条件；发行构建可整体关闭；使用调试命令后 State 与 UI 一致。

### F22：模块 Sandbox 场景

- **职责**：为网格、建造、六边形地图、战斗和 UI 提供独立实验场，降低启动完整游戏的成本。
- **核心接口**：`GridSandbox.tscn`、`BuildingSandbox.tscn`、`HexMapSandbox.tscn`、`BattleSandbox.tscn`、`UISandbox.tscn`。
- **目录位置**：`Scenes/Dev/`。
- **Codex任务**：先建立可单独运行的 Grid 与 HexMap sandbox；约定每个核心模块新增可视化行为时是否需要 sandbox 更新。
- **验收标准**：至少两类 Sandbox 可单独从编辑器启动；无需读档即可展示预设数据；Sandbox 不成为正式游戏逻辑的唯一入口。

### F23：资源加载、Group 与节点约定

- **职责**：统一小资源预加载、Definition 注册、重资源按需加载以及必要 Godot Group 的命名。
- **核心接口**：加载规则；Group 名称如 `interactable`、`building_view`、`survivor_view`、`debug`。
- **目录位置**：`Docs/游戏程序相关/架构/`、`Src/Data/Loading/`、各 Scene。
- **Codex任务**：记录何时可使用 `preload()`、何时应经 DataRegistry、何时延迟加载；建立允许的 Group 清单与用途，禁止同义 Group 泛滥。
- **验收标准**：Definition 加载不分散在 UI 中；相同概念不会出现多个拼写不同的 Group；大型内容不因启动时无差别加载而阻塞基础流程。

### F24：基础输入与可访问性预留

- **职责**：建立输入动作、焦点行为、缩放/文字可读性和设置数据的最小公共基础，避免 UI 完成后整体返工。
- **核心接口**：InputMap action（`cancel`、`confirm`、`open_debug` 等）；`SettingsState`；`SettingsService` 最小接口。
- **目录位置**：`project.godot`、`Src/UI/`、`Src/Core/State/`。
- **Codex任务**：定义基础键鼠操作、Esc/取消行为、UI 焦点规则；预留文字缩放、音量、屏幕震动等设置的数据结构，但不制作完整设置菜单。
- **验收标准**：键盘可关闭顶层窗口；主要交互不只依赖鼠标单一输入；设置状态可序列化且不会与存档核心状态混淆。

### F25：跨平台输入与触摸手势框架

- **职责**：把鼠标、键盘、手柄与触摸输入转换为一致的游戏操作意图，避免玩法系统判断具体设备。
- **核心接口**：`InputService.get_action_state(action: StringName)`、`pan_requested(delta: Vector2)`、`zoom_requested(amount: float)`、`world_tap_requested(position: Vector2)`、`world_long_press_requested(position: Vector2)`。
- **目录位置**：`Src/Core/Input/`、`Docs/游戏程序相关/架构/PlatformInput.md`。
- **Codex任务**：定义语义化输入动作，如 `confirm`、`cancel`、`pan_map`、`zoom_map`、`place_building`；实现鼠标滚轮/拖拽与双指缩放/单指拖拽/长按之间的适配层；禁止 BuildingSystem、WorldSystem 直接读取触摸事件。
- **验收标准**：同一个“放置建筑”“平移地图”“缩放地图”“取消”操作可由桌面和触摸输入触发；地图系统只接收统一意图；触摸拖拽不会误触为点按或建造确认。

### F26：响应式 UI、安全区域与平台布局

- **职责**：让 HUD、菜单、弹窗和工具提示能适应桌面窗口、平板及手机横屏，并避免刘海、圆角和系统手势区遮挡关键信息。
- **核心接口**：`ResponsiveUI.apply_layout_profile(profile: StringName)`、`SafeAreaService.get_content_rect() -> Rect2`、`UILayoutProfile`（desktop / tablet / phone）。
- **目录位置**：`Src/UI/Responsive/`、`Scenes/UI/`、`Docs/游戏程序相关/架构/PlatformUI.md`。
- **Codex任务**：规定所有 UI 使用 Anchor、Container、Size Flags；建立基于可用宽度的布局档位；建立安全区域边距、触摸热区最小尺寸和桌面/移动端 HUD 差异规则；为主要窗口制作占位布局。
- **验收标准**：在 16:9 桌面、16:10 桌面、平板横屏和窄屏手机横屏下，关键资源、确认/取消按钮和弹窗标题均不被遮挡或重叠；移动端可使用更紧凑的 HUD 和展开面板，而不是直接缩小桌面 UI。

### F27：性能预算、画质档位与真机验证

- **职责**：从原型阶段控制移动端帧时间、内存、纹理、粒子和渲染成本，并允许根据设备能力降低表现开销。
- **核心接口**：`PerformanceProfile`、`QualitySettings.apply_profile(profile: StringName)`、`PerformanceMetrics`；画质档位 `low` / `medium` / `high`。
- **目录位置**：`Src/Performance/`、`Docs/游戏程序相关/架构/PerformanceBudget.md`、`Tools/`。
- **Codex任务**：设定第一版目标帧率、目标最低 Android 设备档位和初版预算；让海面特效、粒子、阴影/光照、动画频率、纹理质量和地图显示密度可由画质档位控制；建立桌面、常见 Android 与低端 Android 的真机测试记录模板。
- **验收标准**：低画质档位可显著减少粒子、特效或地图显示负担且不破坏核心可玩性；性能问题能通过指标和设备记录复现；每个垂直切片至少在一台真实 Android 设备上验证，而不只在编辑器中运行。

## 6. 6 个推荐实施 Batch

### Batch 1：工程与规则（F01–F04）

建立工程设置、Git 卫生、目录、AGENTS.md、架构规范、ID 规则。此批次结束后，所有后续任务有明确的文件位置和代码边界。

### Batch 2：状态与数据（F05–F07）

实现 GameSession / GameState、Definition / Instance 模型及 DataRegistry。此批次不做真实玩法，只完成可构造、可加载的基础数据闭环。

### Batch 3：统一运行时基础（F08–F11）

实现命令与信号约定、SimulationClock、RandomService、SaveService / Migrator。此批次结束后，系统已有可靠的输入、时间、随机与存档基础。

### Batch 4：流程、跨平台输入与界面骨架（F12–F13、F24–F26）

实现 SceneRouter、UIRoot、窗口层级、基础输入、鼠标/触摸适配及响应式布局。建立主菜单 → 空游戏场景 → 主菜单的流程；用占位 UI 验证桌面与手机横屏，不制作正式美术 UI。

### Batch 5：两套空间坐标与对象边界（F14–F17）

实现等距 GridMath、RaftGrid、HexGrid，以及 Definition/Instance/View 的绑定与销毁约定。此批次重点是纯逻辑正确性，不做完整建造或地图内容。

### Batch 6：质量、性能与开发效率（F18–F23、F27）

实现日志、GUT、headless 验证、DebugPanel、Sandbox、资源与 Group 约定、画质档位和真机验证记录。此批次结束后，Codex 应可独立验证多数框架和后续玩法任务。

## 7. 框架阶段明确不实现的内容

以下内容可以有接口或数据占位，但不进入本阶段的正式开发与平衡：

- 完整竹筏建造、升级、拆除与装饰内容。
- 完整背包、资源生产链、饥饿/口渴、NPC 工作与寻路。
- 正式伙伴卡牌、技能配置、队伍组合与升级数值。
- Boss、回合制战斗规则、伤害公式、掉落和数值平衡。
- 完整六边形世界、航行、区域内容、POI、天气与随机事件。
- 大量剧情、任务、文案、美术、音频、特效与正式 UI 视觉。
- 网络、账号、好友、排行榜、云存档、联机、服务器及平台 SDK。
- ECS、C#、SQLite、复杂依赖注入框架或大量第三方插件。

框架阶段只回答“未来功能如何接入”，不提前实现“未来功能的全部细节”。

## 8. 框架阶段总体验收

框架准备完成必须同时达到以下结果：

1. 新项目可启动，且 headless 启动/验证命令通过。
2. `AGENTS.md`、架构文档、编码规范和数据规范存在且互不矛盾。
3. 能创建、保存、重启并加载一个最小 GameState，且保留 `save_version`。
4. DataRegistry 能加载至少一份 ItemDefinition 和 BuildingDefinition，并验证 ID。
5. 同一随机种子能重现随机结果；SimulationClock 能暂停和倍速。
6. GridMath 与 HexGrid 有自动测试；RaftGrid 能验证最小占格规则。
7. 空 Game Scene、UIRoot、SceneRouter 和至少一个 Sandbox 可以独立工作。
8. GUT 及统一验证命令能够在无图形窗口的环境运行。
9. Debug 工具仅在开发环境可用，并经受控接口改变状态。
10. 同一项核心操作可由桌面与触摸输入触发；手机横屏与桌面窗口中的关键 UI 均不被安全区域或分辨率遮挡。
11. 项目拥有低/中/高画质档位的最小实现，并记录至少一台真实 Android 设备上的垂直切片验证结果。
12. 任意新玩法任务都能明确回答：数据在哪里、规则属于哪个 System、View 如何更新、如何保存、如何测试，以及桌面/移动端如何操作与验证。

## 9. 框架完成后的第一个 Gameplay 开发阶段

第一个 Gameplay 阶段建议命名为：**竹筏建造基础垂直切片**。

实施顺序：

```text
RaftGrid
  → 初始 3×3 甲板
  → ItemDefinition / InventoryState
  → InventorySystem
  → BuildingDefinition
  → PlaceBuildingCommand
  → BuildingSystem
  → 等距放置预览与 BuildingView
  → 保存 / 读取验证
```

最小可玩目标：玩家拥有木材，选择一个 1×1 甲板或示例建筑，在合法网格放置它；非法位置得到明确反馈；退出并读档后放置结果仍存在。此阶段暂不引入生产、幸存者、航行或战斗。

## 11. 最终结论

《沧海余生》的开发前框架不追求复杂或一次性覆盖所有未来玩法，而是建立一条稳定的扩展路径：

```text
Definition 数据
  → Instance 状态
  → System 规则
  → Command / Signal
  → View 表现
  → Save / Test / Debug 验证
```

当 F01–F27 全部通过验收后，项目便具备让 Codex 按模块持续开发桌面端与移动端玩法的基础。下一步直接进入“竹筏建造基础垂直切片”，以最小可玩循环验证架构，而不是继续扩充抽象框架。
